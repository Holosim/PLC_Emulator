## Recurring patterns across these closeouts

- **"Already current" pattern** (issues #7/#8/#11/#12/#14/#15/#16): when Test Engineer's post-merge regression pass reports the RTVM already shows the correct `Verified`/commit-SHA state, no doc edit is needed — just comment confirming and close.
- **3-arg `Evaluate` signature ripple**: issue #11 added a 3rd `elapsed: TimeSpan` param to `IInstruction.Evaluate`. Every sibling instruction-group branch cut before #11 merged (#10, #12, #13, #14) hit a real (not silent) merge conflict adopting it at CI/CD-merge time. Expect the same for any future instruction-group branch that predates a shared-interface signature change.
- **`PlcController` ctor signature ripple**: same pattern as above, but for the 3rd `DriverResolver driverFactory` ctor param added by CORE-209 (#15). Branches cut before #15 merged (#18) that added new tests calling the old ctor broke at merge time; fix is always the same no-op-resolver pattern already established in `ScanEngineTests.cs`.
- **Label-reconciliation recovery** (issues #10, #13): when Holosim's automated reconciliation flags mutually-exclusive status labels, verify real state via `git merge-base --is-ancestor` + RTVM content before acting — the true state is often much further along (even fully complete) than the stale label implies. See [[feedback-label-reconciliation]].
- **Feature branches lag `main`**: `docs/RTVM.md` edits on an `issue-<n>` branch can be missing status updates that landed on `main` from sibling issues merged after `issue-<n>` was cut. `git merge origin/main` into the feature branch before editing is the fix (non-overlapping RTVM table rows merge cleanly); if editing directly on `main` instead (the more common case once a branch is already merged), `git pull --ff-only` first if the local clone is stale.
