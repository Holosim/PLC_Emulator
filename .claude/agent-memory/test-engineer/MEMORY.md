## Recurring failure patterns

<!-- Bugs or regressions that have shown up more than once, and what
     actually fixed them, so they're recognized faster next time. -->

- Watch for a new unthrottled/high-frequency loop sharing a lock with a
  low-frequency path (e.g. TCP accept) — first seen issue #30 (OUT-403's
  free-running scan loop starving `TcpJsonServer`'s accept path via
  `_clientLock`), fixed by splitting the accept lock from a dedicated
  write lock the accept path never touches. When a new hot loop lands,
  explicitly re-test any other `Verified` row whose code touches the
  same lock/resource, don't rely on the SE's own "no regression" claim
  if their manual check didn't actually exercise concurrent contention.
  When such a fix comes back for re-test, re-verify with the *same*
  live concurrent-load scenario that caught it, not just a clean
  full-suite pass. See [[harness-dotnet-scaffolding]] for the full
  repro/isolation technique.
